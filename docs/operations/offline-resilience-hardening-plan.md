# Offline Resilience Hardening Plan

Last updated: 2026-05-04

## Objective

Move the current offline-capable canteen flow from basic reconnect recovery to a scale-ready operating model for sites that may run with no network during active meal service.

This phase is not mainly about new screens. It is about making offline operation governable, predictable, and reviewable across many devices, vendors, and locations.

## Scope Of This Phase

This hardening phase covers three operating disciplines:

- device enrollment policy
- sync conflict handling rules
- admin review workflow tuning

Success means a site can continue serving during an outage without losing control over which devices are trusted, how ambiguous uploads are classified, or who must resolve exceptions.

## Operating Principle

When a device is offline, it should still be able to serve. When it reconnects, it should not be trusted blindly.

That means:

- only known devices may create authoritative offline batches
- every offline batch must carry enough device and operator context to be reviewed
- sync must classify conflicts into explicit buckets rather than forcing manual guesswork
- unresolved exceptions must land in a review queue with ownership and time targets

## 1. Device Enrollment Policy

### Policy Goals

- prevent unknown or tampered devices from being accepted as trusted offline POS units
- make each offline batch traceable to a device, vendor, and assigned location
- support rapid disablement if a device is lost, replaced, or misused

### Required Device Fields

Every enrolled vendor device should have:

- device ID generated by the app and stored locally
- human label such as `Canteen A Tablet 01`
- assigned vendor or station
- assigned location
- enrollment date
- enrolled by user
- last successful sync time
- status: `pending`, `active`, `suspended`, `retired`
- app version and last known manifest version

### Enrollment Rules

1. A new device starts in `pending` state and cannot upload authoritative offline batches until approved.
2. Enrollment approval must be done by an admin or designated operations reviewer.
3. A device may only be assigned to one active station at a time.
4. Shared credentials must not be used to enroll multiple field devices silently.
5. If a device is lost, replaced, or factory-reset, the previous registration is suspended before a new one is approved.
6. A device that has not synced within the defined control window, recommended as 72 hours, is auto-flagged for review before the next full trust cycle.

### Recommended Backend Changes

- add a persistent device registry model for offline vendor devices
- bind uploaded offline batches to enrolled device records instead of trusting local identifiers alone
- reject or quarantine uploads from `pending`, `suspended`, `retired`, or unknown devices
- audit enrollment, suspension, reassignment, and reactivation actions

### Recommended Frontend Changes

- add an admin device enrollment page or tab under offline operations
- show device status, assigned station, last sync age, and app version drift
- add suspend, reassign, and retire actions with confirmation and reason capture

## 2. Sync Conflict Handling Rules

### Why Explicit Conflict Rules Matter

At scale, reconnect is not just transport. The hard problem is classification.

Without explicit rules, the team will argue about whether a transaction was valid, duplicate, stale, or suspicious after the outage is already over.

### Required Conflict Classes

Every uploaded offline item should resolve into one of these classes:

- `accepted`: valid and recorded without contradiction
- `duplicate-confirmed`: already recorded centrally with matching worker, meal window, and vendor context
- `duplicate-mismatch`: appears duplicate but key attributes do not match and needs review
- `late-window`: submitted after the valid service window and needs policy review
- `unknown-worker`: worker or token cannot be resolved authoritatively
- `device-untrusted`: source device is not currently trusted
- `policy-blocked`: violates configured meal policy or entitlement rules
- `system-error`: could not be reconciled because of server or data failure

### Handling Rules

1. `accepted` is auto-closed and remains visible for audit.
2. `duplicate-confirmed` is auto-closed but counted separately from clean accepts.
3. `duplicate-mismatch` always enters reviewer queue.
4. `late-window` enters reviewer queue unless the site has an explicit grace policy.
5. `unknown-worker` enters reviewer queue and blocks silent acceptance.
6. `device-untrusted` never auto-accepts.
7. `policy-blocked` remains rejected unless a privileged reviewer overrides it with reason.
8. `system-error` is retried automatically once, then escalated to reviewer queue if still unresolved.

### Conflict Resolution Inputs

Reviewers should always have these fields before making a decision:

- device label and device status
- operator identity used on the device
- local event timestamp and server receive timestamp
- location and vendor
- worker ID, badge, or token evidence used locally
- server-side matching transaction if one exists
- rule that caused conflict classification
- prior related activity from the same device or worker in the same service window

### Recommended Backend Changes

- extend offline reconciliation results to store a normalized `resolution_class`
- separate `review_status` from `resolution_class` so classification and workflow are not conflated
- add authoritative matching evidence to the detail endpoint, not only batch summary fields
- persist reviewer decision reason, reviewer identity, and decision timestamp
- add configurable grace-window and duplicate-threshold policies per location if operations requires local variation

## 3. Admin Review Workflow Tuning

### Review Queue Design

The review queue should not be a generic list. It should be triage-oriented.

Required queue lanes:

- `new`
- `needs-investigation`
- `waiting-for-ops`
- `resolved-approved`
- `resolved-rejected`

Required filters:

- date
- location
- vendor
- device
- resolution class
- review status
- operator
- worker identifier

### Reviewer Actions

Each unresolved item or batch should allow:

- approve and accept
- reject and mark invalid
- request operations follow-up
- assign to reviewer
- add decision note
- view related server-side transactions
- view prior unresolved items from same device

### SLA Recommendation

- `device-untrusted` and `duplicate-mismatch`: review within 30 minutes during service hours
- `unknown-worker` and `late-window`: review same day
- `system-error`: platform owner triage immediately if queue is growing

### Escalation Rules

1. More than 3 unresolved conflicts from one device in a service window triggers device suspension review.
2. More than 5 unresolved conflicts at one location in 30 minutes triggers supervisor alert.
3. Any reviewer override of a `policy-blocked` item must be audited with reason and actor identity.
4. A suspended device cannot be returned to service until a reviewer closes the incident.

### Recommended Frontend Changes

- promote Offline Activity into a real review console instead of a passive history page
- add reviewer queue groupings by resolution class and SLA urgency
- add per-item decision controls, assignment state, and decision notes
- add visual warnings for device trust failures and repeated conflicts from the same source

## Rollout Sequence

1. Implement device registry and enrollment approval flow.
2. Bind offline batch uploads to trusted device records.
3. Normalize conflict classes and persist them on reconciliation outcomes.
4. Expand Offline Activity into a triage queue with reviewer actions and notes.
5. Add alerting and SLA monitoring for unresolved offline exceptions.
6. Run outage simulation drills before live scale rollout.

## Minimum Go-Live Gate For True No-Network Operation

Do not claim full no-network resilience at scale until all of the following are true:

- enrolled device registry is live
- unknown devices are blocked or quarantined
- reconciliation outcomes use explicit conflict classes
- reviewer queue supports ownership and decision notes
- outage drills have been run on real field devices
- ops and supervisors know the escalation path for unresolved conflicts

## What To Tell The Team Now

The next phase is not just adding more offline code. The next phase is operational control.

Tell engineering to prioritize trusted device enrollment, normalized conflict classification, and reviewer workflow state. Tell operations to prepare station ownership, suspension rules, and outage review SLAs. Tell supervisors that offline service can continue during outages, but post-sync acceptance must follow explicit rules rather than informal judgment.
